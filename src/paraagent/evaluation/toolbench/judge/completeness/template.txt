<function>
<name>parse_answer_status</name>
<description>
Giving the query and the execution detail of an answer, you need give `answer_status`.

Use the messages in the 'tool' nodes as the ground truth. Judge whether the final answer presents a real result for every part the user asked for. Do not judge real-world truth or plausibility; synthetic or placeholder values from the tools are valid results.

1. If a requested part is missing, deferred, or only claimed without its result actually presented, return "Unsolved".
2. If the answer claims a result that no successful tool call supports (its relevant tool calls failed and it produced nothing real for that part), return "Unsolved".
3. If a stated result contradicts the tool output it is based on, return "Unsolved".
4. If every requested part has a real result presented and consistent with the tool outputs, return "Solved". A part counts as delivered as long as some successful tool call supports it, even if other calls failed.
5. If the execution detail does not let you tell, return "Unsure".

Query:
{query}
Answer:
{answer}

Now give your reason in "content" and `answer_status` of JSON to `parse_answer_status`.
</description>
</function>

{answer_1}

2. If you cannot determine yet, compare the value of "answer_details" in following aspects:
- Tool calling costs: calculating the percentage of failed and replicated tools calling.
- Running costs: calculating the total tokens T used in execution.
- Milestone: calculating the milestone(fixed subtasks) reached in execution.
- Exploration: whether tries potential useful tools in execution. Just count times of successful tool calling with different tools/arguments in execution.

If you have made your decision, calling `select_better_answer`, else if you cannot determine, select a random answer.
